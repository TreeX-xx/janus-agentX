# Workspace I/O batches

Checkpoint operations and workspace edit/create/delete transactions share the exported process-local WorkspaceIoQueue. Nested helpers reuse their transaction and must run sequentially, without detached work. Existing directory aliases use a canonical realpath transaction key; missing paths retain their resolved lexical key. One batch runs at a time; a directory transaction retains ownership when another directory runs at a boundary. Idle collection releases directory ownership between batches. The limits are 32 files per batch, 64 waiting logical tasks, and a shared 20ms rest between background batches. Suspended continuations retain their existing task slot. Queue saturation rejects explicitly; cancellation removes unstarted work and stops started work at cooperative boundaries.

Workspace create/edit/delete no longer create persistent checkpoints or resolve snapshot storage. Their path/policy checks, expected hashes, commit revalidation, exclusive creation, atomic replacement, queue and cancellation remain. Per-call diff previews remain independent of checkpoint blobs. This retires automatic historical recovery for ordinary file tools, including uncommitted deletions; approvals and Git do not replace content backups. Legacy checkpoint engine exports remain for compatibility, but the tools do not invoke them. The CLI no longer labels a legacy checkpoint id as an undo guarantee. Main verification: all 378 core tests pass with one existing skip, including mutations under an unavailable storage resolver and assertions that no checkpoint id or files are produced. Desktop ownership and data cleanup remain with JanusX.

Initialization shares its in-flight promise and loads only existing metadata, without creating directories. Identical in-flight count queries share one scan; empty requests do not scan. Snapshot capture fails instead of publishing partial file maps. Bounded content reads detect growth and changes during capture. Checkpoint files, indices and restored contents use temporary files and rename. GC runs idle, refreshes references after yielding, and coalesces concurrent mutations into a dirty follow-up pass. Unknown, malformed or unreadable checkpoint metadata disables automatic blob collection for that loaded directory, favoring retention over accidental loss.

readIoFile/writeIoFile use 64 KiB buffers and cooperative yields. createIoWriteStream uses standard Writable backpressure and closes a pending open even if destroyed early. node-hosts command.run streams live output through it, retaining the existing 8 KiB previews and 10 MiB per-stream capture limits. External processes pause when the log writer needs drain. Log failures do not change the command result; missing logs omit logPath.

Hosts can configureWorkspaceStorage before consumers start. The resolver returns launch, checkpoint and log paths plus optional retentionStartedAt; an uninjected CLI keeps the legacy .janusX layout. Checkpoint operations revalidate resolved storage before using loaded state, so directory replacement or migration cannot retain an old checkpoint/blob cache. releaseWorkspace drops loaded state inside the host's queue transaction; idle GC stops when its state has been replaced. Age retention uses max(original createdAt, retentionStartedAt), while the existing count limit remains unchanged. Hosts own persisting that timestamp once at successful explicit migration; ordinary initialization does not reset it.

Long-lived sync and node-hosts background log writers acquire a process-local storage usage guard before resolving paths and release it after flush or failure. Hosts suspend new command starts during a switch and reject migration while a writer is active. This is a small usage counter and switching marker, not a separate scheduler or cross-process lock. command.read-log accepts an active workspaceId, filename logId and byte page; it defaults to 16 KiB, caps at 64 KiB and rejects path escape, linked files and workspace mismatch. command.run returns logId/logReadTool for external storage and preserves a relative logPath where available.

JanusX P4 also protects workspace create/edit/delete calls across cooperative yields. Parent storage usage includes descendants; a release callback lets the host retry work previously deferred by an active consumer. Callers release once even after errors or cancellation. The host keeps one expiry timer and owns persistent retention and purge intent; this shared package adds no cleanup policy or thresholds. `workspaceIo.idle` drops inherited foreground context and accepts an optional ownership flag: the default still releases between batches for checkpoint GC, while host lifecycle transactions retain their registry lane and yield the I/O lane to other directories. Core verification is 24 files, 380 passing tests and one existing skip, including descendant guards, single release events, detached maintenance context and retained registry ownership; node-hosts has 64 passing tests in eight files.

Main verification: `npm test --workspace=@janus-agent/agent-core --workspace=@janus-agent/node-hosts` passes 377 core tests in 24 files with one existing skip, plus 64 node-hosts tests in eight files. Both packages build. Real filesystem regressions cover eight terminals, Unicode, cold metadata-only initialization, coalesced queries, failed/cancelled capture, atomic chunk output, GC interleaving and destroyed streams. node-hosts tests include a real 100 MiB subprocess and private-storage sync/background log reads, writer protection and spawn-failure release. JanusX adds migration, cache/alias identity, config inheritance and browser tests; its owning Note contains commands and results. This is Main-agent verification, without an independent reviewer.

This reduces duplicated work and overlap; it does not cap physical disk utilization or coordinate independent processes. Existing snapshot path policy remains unchanged. Paths/index maps grow with file count; Git output has a 16 MiB bound, and individual hashes, JSON encoding/decoding and diffs still contain synchronous work. Background rest can slow cold scans; canonical key checks add a small synchronous filesystem lookup per operation. Slow disks, remote hosts and long-running multi-instance behavior need later representative validation. JanusX owns its userData migration implementation; Hook isolation and lifecycle cleanup remain separate stages.
